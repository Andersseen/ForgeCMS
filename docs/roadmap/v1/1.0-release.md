# 1.0 RC → 1.0 — Make the compatibility commitment

Status: proposed. Entry: 0.12 candidate evidence accepted; final public surface frozen. Owner: maintainer/release
owner with independent QA review. No implementation feature backlog belongs in this stage.

## Goal

Make a realistic compatibility commitment on the exact tested package artifacts.

## Why now

0.12 already combines certification and RC preparation. Proceed directly to candidate use and
release; no further minor exists purely to record that certification is complete.

## Existing foundation

Use the current fixed-family Changesets workflow, packed verifier and consumer suites, plus the
profile, Angular/SSR, admin and upgrade evidence accumulated by 0.5–0.12.

## Scope

L01 preparation belongs to the 0.12 checkpoint; L01 candidate production, L02 defect-only observation
and L03 authorized publication complete this stage. Record exact artifact identity throughout.

## Non-goals

No new features, provider expansion, admin redesign or mandatory plugins/CLI/email/OAuth.

## Dependencies

R01–R04, P03 complete D1/R2 and libSQL/S3 profiles, U03 surface freeze and release-owner acceptance.
Publishing/deploying requires the relevant session authorization; this roadmap grants none.

## Implementation packets

### L01 — Produce and validate a release candidate

- **Depends on:** R01–R04. **Scope:** existing Changesets/release machinery, candidate artifacts and
  dossier. No manual per-package version drift; keep the existing fixed family, including any approved S3 package membership from P01.
- **Deliver:** validate the existing workflow's prerelease behavior and explicit prerelease dist-tag
  before publishing a candidate. Ensure `1.0.0-rc.*` cannot accidentally replace the stable tag.
  Prepare exact artifacts, commit, release notes and compatibility/migration document first.
- **Acceptance:** candidate packages have aligned versions, correct exports/dependencies/files,
  build artifacts and provenance configuration. Verify the exact candidate artifacts through the
  full release matrix. Publishing/deployment remains a separately authorized release action.
- **Evidence:** artifact identity, workflow/dry-run inspection, full command results and changelog.
  Do not assume the normal main-branch release workflow already handles prerelease tags safely.

### L02 — Observe real consumer use and fix only defects

- **Depends on:** L01. **Scope:** candidate bug triage/regressions/docs. No features, new components,
  provider expansion or dependency upgrades unrelated to a proven blocker.
- **Deliver:** two distinct consumer validations: minimal content/admin fixture plus a separately
  maintained real project when available. If external access is unavailable, record the gap and use
  an independently assembled consumer; do not imply an external team validated it.
- **Acceptance:** an RC observation period with real use in maintained consumers, critical journeys
  and multiple clean full certification runs on the final candidate; no unresolved release blocker
  or unexplained flakiness. Choose duration and additional reruns from actual changes and feedback,
  not a universal calendar/count rule. A material auth/data/API fix restarts relevant observation
  and affected/downstream validation; cosmetic docs do not automatically restart it.
- **Handoff:** dated consumer feedback, regressions/fixes, final issue classification and owner.

### L03 — Release and verify the published result

- **Depends on:** L02 and explicit release authorization. **Scope:** release actions and verification,
  not code implementation. Confirm all final gates refer to the same accepted commit/artifacts.
- **Deliver:** publish the fixed package family as 1.0 through the approved workflow, publish migration
  and compatibility notes, then clean-install the registry artifacts and run export/type/production
  smoke verification. Record how a partial multi-package publish is resumed safely; do not unpublish
  existing versions or silently substitute different content under one version.
- **Acceptance:** all expected packages/versions are available, registry consumer builds and completes
  a smoke journey, release tag points to accepted code, docs match published artifacts. If publication
  cannot be verified, report incomplete release rather than declaring success.
- **Handoff:** support owner, issue/security reporting paths, 1.0.x patch policy, first maintenance
  backlog and archived candidate evidence. Commitments are compatible fixes in patch releases,
  additive compatible features in minors and breaking public changes only in a major.

## Acceptance criteria

- [ ] Public export/route/default/error/type and support matrices complete and accurate.
- [ ] Full common, coverage, type, contract, durable backend, browser and packed-consumer gates pass.
- [ ] Access, session, concurrency and fault cases have explicit regression evidence.
- [ ] Upgrade and backup restoration rehearsed; D1/R2 and libSQL/S3 durable profiles verified, including staging and files.
- [ ] No unresolved critical/high safety or data-integrity defect, no hidden test waiver.
- [ ] RC use and final candidate evidence complete; exact artifact identity recorded.
- [ ] Publication authorized and registry artifacts subsequently verified.
- [ ] Release/migration/support documentation available and aligned with the artifacts.

Only then mark 1.0 shipped in STATE. A broad component catalogue, email adapter, CLI, plugins,
presigned uploads, GraphQL and visual history/preview are not part of this checklist.

## Required tests

Full QUALITY candidate matrix, both durable file profiles, typed Angular and production SSR/public
hydration, admin, security/concurrency regressions, strict peers, schema upgrade and backup restore.
Verify exact candidate artifacts before publication and registry artifacts afterward. Multiple clean
runs support observation; neither elapsed time nor a one-off green run proves release readiness.

## Release gate

All checklist items pass on accepted artifacts; observed consumer feedback has no unresolved blocker.
Only after authorized publication and registry verification mark 1.0 shipped in STATE. Publication
failure remains incomplete release work, not a reason to claim success or silently replace artifacts.
