# 0.11 — SSR and hydration with request isolation

Status: proposed. Outcome: public content is present in server-rendered HTML and hydrates safely.
Entry: C01–C03 configurable transport and honest types. Finding: F14.
Owner: Angular/Analog integration implementer; reviewer checks identity and cache boundaries.
Read: Angular service/resources/session, tiny-project server runtime/Vite setup, current linker
export, Analog host configuration. Verify current framework APIs from primary docs when implementing.

## S01 — Request-scoped server transport

- **Depends on:** C01–C03. **Scope:** Angular request/SSR integration and one consumer fixture;
  no new `@forge-cms/analog` package unless separately approved outside this scope.
- **Deliver:** explicit server base URL and per-request identity context. Choose Local API rendering
  or HTTP transport for each documented host path; do not fabricate Requests just to call Local API.
  Ensure injection/caches cannot share credentials or results across users.
- **Acceptance:** relative browser URL works in browser, configured absolute URL works server-side;
  no browser global is accessed during SSR. Concurrent anonymous/A/B requests return only their own
  allowed content. User-supplied URLs cannot cause credential forwarding to untrusted origins.
- **Tests:** concurrent request integration with distinct identities and server-side rendering of
  public/private routes. Include auth-service initialization, errors and request teardown.
- **Handoff:** precise host wiring guide and server/client request contract for S02.

## S02 — Safe hydration and transfer behavior

- **Depends on:** S01. **Scope:** Angular SSR/resource transfer behavior and fixture tests; no global
  cache service or framework-wide optimization project.
- **Deliver:** define which public reads can transfer from server to client, stable transfer keys,
  expiry/invalidation and error behavior. Default to not transferring personalized/authenticated
  content unless a separately proven request-bound design is approved.
- **Acceptance:** public page HTML contains real content before JS; hydration reuses the intended
  public response without a duplicate initial fetch. Auth responses, tokens, cookies, hashes and
  other private data do not appear in HTML, transfer state or another request. Navigation/locale/query
  changes produce the right new data; failure does not poison later requests.
- **Tests:** HTML/transfer assertions, request-count assertions, concurrent-user isolation and browser
  hydration with console-error checks against a production build.
- **Handoff:** documented cache/transfer semantics for public consumers.

## S03 — Production SSR consumer journey

- **Depends on:** S01–S02. **Scope:** tiny-project or a minimal independent packed consumer,
  production server test command and docs. No unrelated www landing redesign.
- **Deliver:** publish one post through the existing admin, render it publicly by slug, change it,
  and verify the documented refresh/cache behavior. Keep server routes thin and only use exports.
- **Acceptance:** built server, not static Vite preview, serves SSR HTML; hydration has no linker/JIT
  error; reload and navigation preserve correct data. Draft/private content remains hidden. A second
  unrelated consumer can follow the setup without copying repository-private linker code.
- **Tests:** packed production build plus browser journey and no-JS HTML assertion on both supported
  deployment profiles where host runtime differences matter; reuse lower-level backend evidence.
- **Handoff:** production SSR gate and runnable consumer setup used by R01.

## Exit / exclusions

SSR is an observed product path, not an unchecked “SSR-safe” label. Public content and identity
isolation pass, with actual framework compatibility recorded. No new Analog integration package,
universal cache system, SSR redesign of every app or authenticated dashboard SSR requirement.
