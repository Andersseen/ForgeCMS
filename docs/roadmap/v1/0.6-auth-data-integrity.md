# 0.6 — Auth and data integrity hardening

Status: proposed; not implementation authorization. Packet IDs are stable planning references,
not spec numbers, releases or mandatory PR boundaries. Follow [EXECUTION.md](EXECUTION.md).

## Goal

Existing users, sessions and content mutations remain safe under realistic changes, concurrency and dependency failures.

## Why now

Fresh permissions and safe persisted data are immediate user needs. Related auth/data guarantees form one hardening outcome while their implementation responsibilities stay bounded.

## Existing foundation

PBKDF2 users, HttpOnly sessions, signup/signin/logout/me, CSRF, roles, last-admin checks and scoped machine keys already exist. Relations, versions, globals, localization and R2 lifecycle tests already exist. Reproduce the remaining risks before fixing them.

## Scope

H01–H04 cover provisioning, freshness/invalidation and existing auth limits; D01–D04 cover relation/history/global/file consistency. Owners: auth, runtime and database implementers with architecture review of concurrency contracts. Findings F07–F11. Read users/token/cookie/composite adapters, runtime auth/CSRF/operations/relation-integrity/versions/globals/files and shared contracts.

## Non-goals

No new auth product: email/reset, OAuth, MFA, passkeys, magic links, invitations, teams and organizations remain outside 1.0. No generic distributed transaction, jobs or rate-limiter framework; host controls suffice. S3 implementation belongs to 0.10.

## Dependencies

0.5 access/contract foundation. H01 establishes the narrow auth primitive; H02/H03 consume it. D01 checks what content mutations actually need rather than assuming auth primitives provide transactions. D02/D03 can proceed once their listed contracts are settled; they do not wait on unrelated H04 host limits.

## Implementation packets

### H01 — Specify and prove the narrow atomic auth primitive

> **Progress (2026-09-18):** delivered by [spec 059](../../specs/059-conditional-writes-last-admin-invariant.md)
> — `DatabaseAdapter.updateIf`/`deleteIf` (single guarded statement on libSQL/D1), proven with a
> deterministic two-writer probe on real libSQL and real local D1. Its sufficiency table for D01–D03 is in
> the spec §7: enough for last-admin, migration bookkeeping and per-row CAS; **not** for D02/D03, which
> need a multi-statement atomic batch.
>
> **Progress (2026-09-19):** that batch now exists — [spec 060](../../specs/060-atomic-write-batch-first-admin-provisioning.md)
> adds `DatabaseAdapter.atomicWrite` (declarative, database-only, all-or-nothing; InMemory / libSQL
> `client.batch(…, 'write')` / D1 `batch()`), reusing `WriteCondition` and adding `requireApplied`. It is a
> **storage capability only**: D02 and D03 are not migrated to it. Sufficiency for them is recorded in the
> spec §8 — D03's document + version write fits one batch; D02's dependent writes can be one batch but need a
> cross-collection "no referencing rows" guard and a chunking/rejection rule for the 25-operation cap.

- **Depends on:** B02, A01–A04. **Scope:** an approved design and minimal adapter/contract
  implementation in db/cloudflare/testing. No general transaction callback framework.
- **Deliver:** choose storage-supported conditional mutation/uniqueness strategy for one bootstrap
  winner and last-admin safety. Define outcomes for success, conflict, retry, dependency failure and
  unsupported adapter. Record how independent D1/libSQL runtime instances satisfy it; validate current
  platform capabilities from primary documentation at implementation time.
- **Acceptance:** a deterministic two-client probe demonstrates the chosen primitive on real local
  D1 and libSQL; no process-local mutex is offered as multi-instance safety. Unsupported custom
  adapters fail explicitly before enabling affected operations. Any adapter-contract change has an
  exact signature/migration and matching shared tests before H02 starts.
- **Handoff:** approved narrow primitive and evidence. If current storage cannot provide the
  required invariant, choose an explicitly serialized trusted provisioning path; do not fake success.

### H02 — Safe provisioning and last-admin invariants

> **Progress (2026-09-18):** first-admin bootstrap atomic (spec 058); last-admin protection through
> `UsersCollectionAuthAdapter` atomic (spec 059). ~~**Still open:** generic users-collection CRUD bypasses
> the guard~~ (closed by [spec 061](../../specs/061-auth-managed-collection-mutation-boundary.md), below);
> ~~a failed first-user create burns the bootstrap claim~~ (fixed by
> [spec 060](../../specs/060-atomic-write-batch-first-admin-provisioning.md): claim and admin are one atomic
> write; a claim burned before 060 is not auto-repaired — trusted `createUser({ role: 'admin' })` /
> `updateUser` recovers it, see the browser-auth docs).

- **Depends on:** H01. **Scope:** users adapter, bootstrap/signup behavior and thin host wiring,
  auth contracts, tiny-project integration. No invitations/email UI.
- **Deliver:** first-admin creation is explicitly authorized setup, not an accidentally open public
  race; signup remains opt-in and cannot select privilege. Use the approved mechanism for last-admin
  mutations, including two admins removing/demoting themselves concurrently.
- **Acceptance:** concurrent attempts produce exactly one initial administrator; after setup,
  unauthorized bootstrap is rejected. Concurrent deletion/demotion never leaves zero usable admins.
  Invalid role/email/password changes fail consistently. Audit generic users-collection CRUD so it
  cannot bypass protected fields and lifecycle invariants; trusted raw adapter access is documented
  as outside runtime guarantees.
- **Tests:** deterministic barriers with separate runtime/adapter instances; real D1/libSQL tests;
  browser setup/signup/last-admin flows. Ordinary `Promise.all` passing once is insufficient proof.
- **Handoff:** provisioning migration for existing consumers, including first-run setup configuration.

### H03 — Current-user validation and session invalidation

- **Depends on:** H02 and H01 contract. **Scope:** users auth adapter, token/session metadata,
  runtime login/logout/me, shared auth tests. Keep server policy and HTTP wiring together when they form one reviewable responsibility.
- **Deliver:** choose a minimal persisted revocation/version mechanism or session record design.
  Define token lifetime, role freshness, password-change/deletion invalidation, logout scope
  (current session or all user sessions), old-token migration and expired-record cleanup if needed.
  The architect fixes exact semantics before implementation.
- **Acceptance:** demoted/deleted users cannot keep privileged access using old cookies or Bearer
  tokens. Password change invalidates prior sessions; logout invalidates replay according to its
  documented scope. Other valid users stay logged in. Dependency failure is not misreported as invalid
  credentials. Existing scoped machine keys retain their separate lifecycle semantics.
- **Tests:** auth unit/parity/contracts, runtime cookie/Bearer replay, real-backend restart, browser
  refresh/demotion/logout. Test CompositeAuthAdapter routing and outage propagation.
- **Boundary:** do not silently change an explicitly stateless external/signed-token adapter into a
  database-backed one. Document adapter-specific guarantees; users-collection auth must meet 1.0 safety.
- **Handoff:** session behavior consumed by C01 and the admin; schema changes passed to M03 fixtures.

### H04 — Bound auth abuse and finish auth certification

- **Depends on:** H03. **Scope:** documented auth limits, runtime boundary validation and generic
  integration points only where necessary; host configuration and tests. No email/reset service.
- **Deliver:** bounded request/password sizes, clear authentication failure behavior, and an explicit
  supported deployment control for login/signup throttling. Prefer host/platform policy over an
  invented distributed limiter in core; document how portable and Cloudflare hosts apply it.
- **Acceptance:** expensive credential operations are not reachable with unbounded inputs; configured
  throttling has deterministic rejection semantics and does not leak account existence. CSRF,
  cookie flags, signing-secret configuration and redacted logs have regression evidence. A 429
  addition, if used, is captured in the contract/SDK error table.
- **Tests:** bounds/failure unit cases and host-level throttle integration with deterministic clocks;
  auth E2E including generic signup role-escalation attempts. Keep machine auth regression suite.
- **Handoff:** complete auth support matrix and documented operator configuration, common gates.

### D01 — Define the mutation consistency boundary

- **Depends on:** H01 and the relevant H02/H03 storage decisions. **Scope:** design spec and any separately scoped db/cloudflare/testing
  capability extension. Reuse H01's primitive only if it really meets the content invariant.
- **Deliver:** behavior table for single writes, cascade/set-null, document+history, global first write,
  and DB+object-storage lifecycle. State which are atomic, conditionally supported, or compensated;
  exactly when hooks run; what errors mean; what is safe to retry; how partial work is observed.
- **Acceptance:** no claim of a transaction spanning D1 and R2. Multi-row supported destructive actions
  either preserve the invariant on failure or are rejected before mutation on unsupported adapters.
  Any compensation design specifies durable recovery after process termination, not only catch blocks.
  Choose conservative feature restriction over a generic distributed transaction framework.
- **Tests:** real backend capability/fault probe before approval, including independent writers. The
  implementation adds shared contract cases and explicit unsupported behavior.
- **Handoff:** exact adapter/operation contract and fault scenarios for D02/D03/M03.

### D02 — Correct relation lifecycle

- **Depends on:** D01 and A03. **Scope:** runtime relation traversal/delete pipeline, adapter queries
  only as approved, tests. No new relation field kind or arbitrary nested JSON query language.
- **Deliver:** supported matrix for single/many, self references, nested composite/localized fields,
  restrict/cascade/set-null, cycles, transitive references and upload references. Define required-field
  behavior for set-null and access/hooks for dependent mutations before coding.
- **Acceptance:** restrict rejects before any related write; supported cascade traverses the complete
  dependency set once with cycle protection and agreed hook/access semantics. Invalid set-null does
  not create invalid documents. Injected mid-operation failures satisfy D01. Reject unsupported
  combinations at configuration/operation entry, with migration notes for previously accepted input.
- **Tests:** relation unit tests plus contract/runtime tests for self/nested/transitive/cyclic cases,
  many-relations, per-row rules, dependent hook failure and concurrent reference changes on D1/libSQL.
  Replace unbounded full-table scans where supported query primitives already suffice; test bounds.
- **Handoff:** relation guarantee matrix and operator-visible failure semantics. Split traversal,
  dependent mutation policy and backend integration into child PRs if needed.

### D03 — Keep documents and history consistent

- **Depends on:** D01, A01. **Scope:** runtime versions/create/update/restore, schema constraints and
  contract tests required by the approved design. No visual history/diff or scheduling feature.
- **Deliver:** concurrency-safe version identity/ordering, defined retention/cleanup, and consistent
  document+snapshot outcomes. Reuse the authorized restore pipeline from A01; do not copy it.
- **Acceptance:** concurrent updates cannot create ambiguous duplicate version identities; rejected
  writes create no committed snapshot. Faults after a document write do not produce silent divergence
  or an unsafe blind retry. Restore uses current validation and permissions, retains stable document
  identity/system fields and emits intended hooks/history once. Unsupported guarantees fail explicitly.
- **Tests:** real D1/libSQL two-writer scenarios, snapshot failure injection, invalid old-schema
  restore, unique constraints, deleted owner, retention cleanup. Record old-data upgrade needs.
- **Handoff:** history schema/behavior and recovery fixtures for M03.

### D04 — Certify remaining content combinations and files

- **Depends on:** D01–D03, A04. **Scope:** globals/localization/defaults and existing upload lifecycle;
  split global/locale and file-lifecycle work only if independently risky or oversized. No new durable storage adapter.
- **Deliver:** supported option matrix with tests; fix accepted-but-inert global options or reject
  them. Define partial global updates, draft behavior, locale fallback/population and simultaneous
  first creation. Extend existing R2 cleanup tests using D01's DB/storage recovery boundary.
- **Acceptance:** editing one locale preserves others; omitted fields do not unexpectedly reset
  persisted values; supported global depth works; unsupported options are explicit. File upload/read/
  deletion respects permissions, limits and metadata. DB failure after object creation and object
  deletion failure after DB changes produce the documented cleanup/recovery outcome without secret logs.
- **Tests:** global/localization unit and real-backend lifecycle; existing workerd storage fault suite;
  one browser upload lifecycle using the certified R2 profile during R01 if unavailable here.
- **Handoff:** supported combinations, migration effects and all critical fault branches covered.

## Acceptance criteria

No stale privileged sessions, bypassable first/last-admin protections, silent data corruption or false atomicity claims. Retained relation/version/global combinations have tested semantics or explicit safe restrictions with migration notes. Existing valid users/content flows remain usable.

## Required tests

Deterministic separate-runtime D1/libSQL concurrency probes, Local/HTTP auth replay/role tests, relation/history fault injection, R2 cleanup regressions and focused browser user/content journeys. Reuse shared adapter contracts. Common repository gates and applicable [QUALITY.md](QUALITY.md) evidence apply.
Record cached, newly run and pending evidence separately.

## Release gate

All H/D invariants and packet acceptance criteria pass. Publish confirmed security/data defects as current-line patches when ready; this minor completes the coherent lifecycle guarantee. Update setup, password-change, logout and failure-recovery guidance alongside each change, not at final certification.
