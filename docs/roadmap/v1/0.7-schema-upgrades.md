# 0.7 — Upgrade safety

Status: proposed; not implementation authorization. Packet IDs are stable planning references,
not spec numbers, releases or mandatory PR boundaries. Follow [EXECUTION.md](EXECUTION.md).

## Goal

A consumer can evolve persisted schemas and recover data through a documented, tested path.

## Why now

Existing content/auth/history must survive upgrades before 1.0. A narrow migration protocol is enough; a large CLI would delay useful work.

## Existing foundation

Additive D1/libSQL sync, shared schema/index helpers, typed schema definitions and existing real-backend fixtures are implemented.

## Scope

M01–M03: drift/destructive-change detection, versioned execution, seeded upgrades and backup/restore. Owners: database/integration; architecture review of destructive-change policy. Finding F12. Read schema generator, syncSchema, auth/history internal schemas and real schema tests.

## Non-goals

No scaffolding CLI, universal schema diff, automatic rollback for arbitrary destructive changes or additional databases.

## Dependencies

0.6 schema-affecting H/D outcomes. M01 → M02 → M03. P03 extends the same backup/restore proof to S3 in 0.10; S3 does not block the initial upgrade protocol.

## Implementation packets

### M01 — Detect drift and document supported changes

- **Depends on:** D01–D04. **Scope:** schema introspection/planning and tests in db/cloudflare/testing,
  consumer docs. No CLI and no automatic destructive migration.
- **Deliver:** classify added/removed/renamed/retyped fields, required/default changes, index changes,
  reserved/system columns and auth/history changes as safe additive, manual migration or unsupported.
  Preserve simple development `syncSchema`; make production drift visible and actionable.
- **Acceptance:** new optional field preserves data; incompatible type/required/index changes cannot
  silently report full success. Renames are not guessed from one removal plus one addition. Unique
  indexes on duplicate legacy data report a recoverable conflict before claiming schema completion.
- **Tests:** existing schema suites on real D1/libSQL with seeded old rows, JSON/composite/localized
  values and internal tables. Re-running inspection yields the same plan.
- **Handoff:** exact change-classification and startup policy for M02.

### M02 — Minimal reviewed migration execution

- **Depends on:** M01. **Scope:** narrow library/script integration based on existing adapters,
  migration metadata and docs. Any new public export requires its own approved signature.
- **Deliver:** ordered migration identity/checksum/status, exclusive execution policy, preflight,
  applied-history check and interruption/retry behavior. A consumer can invoke the approved path
  from its own deployment tooling; no new `@forge-cms/cli` package is required.
- **Acceptance:** already applied migration is not applied twice; edited applied migration is detected;
  concurrent runners cannot both perform the same unsafe work. Failed migration is identifiable and
  never silently marked complete. Destructive steps require explicit reviewed operator input and
  backup under the consumer's deployment policy. Unsupported rollback is clearly stated.
- **Tests:** seeded upgrade, duplicate invocation, two runners, mid-step failure/restart, checksum
  mismatch and the approved recovery action on D1/libSQL. Do not implement fake SQL transactions on
  a platform that cannot support the required execution model.
- **Handoff:** migration ledger/execution contract, operational commands and recovery instructions.

### M03 — Prove upgrades and backup restoration

- **Depends on:** M02. **Scope:** integration fixtures and documentation; only targeted package fixes
  if the rehearsal exposes a generic defect, with a focused regression and coherent scope.
- **Deliver:** fixtures from a known 0.4.x baseline and each planned schema-changing minor; store
  version/schema provenance. Exercise content, users, hashes, roles, relations, drafts, locales,
  globals and history through the approved upgrade path. Include R2 metadata/object references in
  the backup scope without claiming DB and object storage share a transaction. P03 extends this
  same rehearsal to S3 objects before 1.0.
- **Acceptance:** clean consumer upgrades and can authenticate/read/edit old content; row counts,
  stable IDs and representative values are verified. Restore into an isolated empty environment
  recreates usable auth/content and required files. Document forward fix vs backup restore; never
  suggest that rolling back code alone reverses an incompatible data migration.
- **Tests:** dedicated reproducible upgrade/restore command introduced by this packet for libSQL and
  local D1/R2; no tests against live production data. Record actual restore limitations and duration.
- **Handoff:** upgrade matrix, fixture provenance and runbook used in R01/R03.

## Acceptance criteria

Supported changes preserve data; destructive/unsupported changes are detected and actionable. Applied migration history, interruption/retry, backup and recovery are explicit. Auth/content/files remain usable after the tested restore.

## Required tests

Real D1/libSQL seeded drift/upgrade/concurrent-runner/fault tests and an isolated backup restore, including existing R2 files. Introduce a reproducible command rather than assuming one exists. Common repository gates and applicable [QUALITY.md](QUALITY.md) evidence apply.
Record cached, newly run and pending evidence separately.

## Release gate

M01–M03 complete. An external consumer follows upgrade/recovery guidance without private internals or undocumented edits. Carry subsequent schema-changing fixtures forward through P03 and R01.
