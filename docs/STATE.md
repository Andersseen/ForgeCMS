## TL;DR

The monorepo foundation is done and CI is green. The schema DSL, validation, runtime orchestrator,
CRUD HTTP handlers, and several real adapters (LibSQL, Cloudflare D1/R2) **exist and are tested**.
As of 2026-07-08, `apps/www`'s routes actually delegate to `@forge-cms/runtime` (spec 007), writes
are protected by a real signed-token auth provider with a login page (spec 006), an e2e suite covers
the CRUD+auth flow (PLAN.md P1-4), and the real admin UI (layout, document list, schema-driven form)
lives in `@forge-cms/admin` and is consumed by `apps/www`, not duplicated in it (spec 008). As of
2026-07-20, spec 009 ships real users-collection auth: `UsersCollectionAuthAdapter` stores users
in the configured database with PBKDF2 password hashing, `/api/auth/users` CRUD is protected by
token auth, and the `/admin/users` page can create, edit, and delete users — covered by a dedicated
Playwright e2e test. Spec 010 (also 2026-07-20) adds role-based access control: admins manage users
and have full content access, editors can create/edit/delete documents, and viewers are read-only
across the backend and admin UI. **As of 2026-07-22, Phase 1 of [ROADMAP.md](ROADMAP.md) is done** — the four structural changes that
separate a typed CRUD layer from a CMS: a **Local API** on `ForgeCmsRuntime` (spec 019) with the HTTP
handlers reduced to transport, **access control as functions** returning row-level query constraints
(spec 020), the **complete hook pipeline** including field hooks (spec 021), and **composite fields**
`group`/`array`/`blocks` (spec 022). Spec 018 also fixed the D1 `passwordHash` bug that broke auth on
the only production path, and gave lists real pagination metadata.

**As of 2026-08-21, Phase 0.2 (Trust / Production Hardening), Phase 0.3.1 (Globals), Phase 0.3.2 (Versions), Phase 0.3.3 (Live Preview), Phase 0.3.4 (Localization), and Phase 0.3.5 (Relation integrity) are complete.**
The foundation is now substantially implemented for an experimental `0.0.1`, with many hardening
gaps closed but no broad production-stability promise before `1.0`. Phase 0.2 hardening work
includes: strict unknown-field validation, identifier validation, hardened D1/LibSQL adapters,
consistent API error contract, strict query parameter parsing, secure auth secret handling,
structured logging, upload lifecycle integrity, upload limits, multi-operator query predicates on a
single field, shared `find()`/`count()` read-query preparation, and recursive field hooks inside
composite fields. **Phase 0.3.1 adds Globals** — singleton documents for site-wide configuration
(nav, footer, SEO defaults). Globals use the same field DSL as collections but have exactly one
document, addressed by slug. The Local API exposes `getGlobalDocument()` and
`updateGlobalDocument()`, the HTTP layer provides `GET/PUT /api/v1/globals/[global]`, and the
Angular client has `getGlobal()` and `updateGlobal()`. **Phase 0.3.2 adds Versions** — document
history with automatic snapshots on create/update. Collections can enable versions with
`versions: true` or `versions: { autosave: true }`. The Local API exposes `listVersions()`,
`getVersion()`, `restoreVersion()`, and `createVersion()`. HTTP handlers provide
`GET /api/v1/[collection]/[id]/versions`, `GET /api/v1/[collection]/versions/[versionId]`, and
`POST /api/v1/[collection]/versions/[versionId]/restore`. Versions store complete document
snapshots with metadata (versionNumber, createdAt, createdBy, autosave, label) and support restore
operations. **Phase 0.3.3 adds Live Preview** — preview documents with unsaved changes before saving.
The Local API exposes `preview()` which merges stored data with changes, applies field defaults and
auto-slugs, and supports relation population. The HTTP layer provides `POST
/api/v1/[collection]/preview` (new documents) and `POST /api/v1/[collection]/[id]/preview`
(existing documents). The Angular client has `previewDocument()`. **Phase 0.3.4 adds Localization**
— i18n support for multilingual content. Fields can be marked with `localized: true` and collections
declare supported `locales`. Localized fields store values as objects with locale keys
(`{ en: "Hello", es: "Hola" }`). The Local API accepts a `locale` parameter for create/update/find
operations, resolving localized fields to the requested locale on read and storing per-locale on
write. Locale resolution follows a fallback chain (exact match -> language fallback -> default
locale). **Phase 0.3.5 adds Relation integrity** — cascade, restrict, and set-null on delete.
Relation fields can specify `onDelete: 'restrict' | 'cascade' | 'set-null'`. The default is
'restrict', which prevents deletion if the document is referenced. 'cascade' deletes all referencing
documents, and 'set-null' sets relation fields to null in referencing documents. The delete operation
now checks relation constraints and handles cascade/set-null automatically. A
`findOrphanedDocuments()` utility detects documents with broken relations.

`overrideAccess`, adapter bindings are configurable, the in-memory adapter stamps timestamps and

**As of 2026-08-26, spec 046 adds compound indexes and schema integrity, preparing `0.0.2`.** ForgeCMS
`0.0.1` is published and being dogfooded by an external consumer (Glossa), which hit a real generic gap:
`unique`/`index` were single-field only, and `InMemoryDatabaseAdapter` did not enforce uniqueness at
all, so a compound-uniqueness bug could pass local dev/tests and only fail against real D1/libSQL.
`CollectionDefinition` now takes `indexes?: { fields: string[]; unique?: boolean }[]` for constraints
spanning more than one field (field order is the generated column order); `defineCollection` validates
them (empty `fields`, unknown field, duplicated field, duplicate equivalent indexes). `@forge-cms/db`'s
`resolveCollectionIndexes`/`generateIndexSql` centralize deterministic SQL index generation
(`idx_<collection>_<field...>`, unchanged for existing field-level `unique`/`index` collections), used
by both `D1DatabaseAdapter` and `LibSqlDatabaseAdapter` so they cannot diverge.
`InMemoryDatabaseAdapter` now registers collections on `syncSchema` and enforces the same single-field
and compound unique-index semantics in-process (including SQLite's "NULL is never equal to NULL"
exemption), closing the dev/test-vs-production gap Glossa hit. A conflict from any adapter surfaces as
the same typed error: `@forge-cms/db`'s `UniqueConstraintError` at the adapter boundary, translated by
`@forge-cms/runtime`'s `operations.ts` into its own `UniqueConstraintError` (`ForgeError`, `409`, code
`UNIQUE_CONSTRAINT`, carrying `collection`/`fields`) — the existing generic `ForgeError` → HTTP mapping
in `handlers.ts` needed no changes to return `409` for it. `@forge-cms/testing/contracts` gained
`runDatabaseAdapterConstraintContractTests`, run from all three adapters' test files (InMemory, a real
libSQL `:memory:` database, and a `D1` mock enhanced to enforce unique indexes for real rather than
being hand-waved). Auth (API keys, scopes, etc.) is intentionally deferred to the next branch — see
[docs/specs/046-compound-indexes-and-schema-integrity.md](specs/046-compound-indexes-and-schema-integrity.md).

**As of 2026-08-27, spec 047 adds a typed collection Local API — a pure TypeScript/DX improvement,
zero runtime behavior change.** `ForgeCmsRuntime<TEnv, TCollections>` gains a second, defaulted type
parameter that preserves the registered collection schemas, so `find`/`findByID`/`count`/`create`/
`update`/`delete`/`preview` infer typed collection slugs (autocomplete, unknown slug = compile
error), typed write payloads (unknown fields/wrong value types = compile error), and typed returned
documents (declared fields plus `id`/`created_at`/`updated_at`) — all delegating to the unmodified
`operations.ts` with one isolated result cast per method. `@forge-cms/core` gained the small type
utilities this reuses `CollectionData`/`InferFields`/`FieldValue` to build: `CollectionRegistry`,
`CollectionSlug`, `CollectionBySlug`, `CollectionDocument`, `CollectionInput`, `DocumentMeta`.
`defineField.json<TValue>()` is now generic (a compile-time-only annotation; `defineField.json()`
still infers `unknown`). The interesting part was getting a genuinely-typed runtime to stay
assignable everywhere an untyped one is still expected: `CollectionBySlug`'s lookup uses a
key-remapped mapped type or falls back to `never`-prone `Extract`, and TypeScript's structural
comparison of two _different_ concrete `ForgeCmsRuntime<Env, ...>` instantiations (e.g.
`let runtime: ForgeCmsRuntime; runtime = someTypedRuntime` — the pattern used throughout this
package's own test suite) broke under the naive `Extract<...> extends never ? ... : ...` version;
the fix is recorded in spec 047. The HTTP-handler boundary (`handlers.ts`'s `HandlerOptions`,
`files.ts`'s `FileHandlerOptions`) pins the runtime's collections registry to `any` via a new
`AnyForgeCmsRuntime<TEnv>` export, since request-time collection slugs are plain strings that can
never be statically narrowed — the only change either file needed. Existing broad/untyped consumers
(`CollectionDefinition[]`, or `ForgeCmsRuntime<TEnv>` given only an environment type) keep compiling
unchanged; `apps/www` and `apps/demo-aesthetics` needed zero changes. See
[docs/specs/047-typed-local-api.md](specs/047-typed-local-api.md).

**As of 2026-08-28, spec 048 adds machine auth (API keys), fully generic — no Glossa/domain concepts
anywhere in `packages/*`.** `@forge-cms/auth` gains `ApiKeyAuthAdapter`: secrets are 256-bit random
values from Web Crypto (`crypto.getRandomValues`), never persisted (only a SHA-256 digest, compared in
constant time), and the plaintext (`<prefix>_<id>_<secret>`, prefix configurable, default `'forge'`) is
returned exactly once, at creation — `listApiKeys`/`getApiKey` never expose the hash or secret. Keys
carry generic `scopes: string[]` and consumer-defined `metadata`, plus `expiresAt`/`revokedAt`; an
expired, revoked, unrecognized, or hash-mismatched key all fail the same generic, non-leaking way.
Persists through the configured `DatabaseAdapter` in an internal system collection
(`_forge_api_keys`, own `access` rules deny everything as defense in depth) that is never part of a
consumer's `config.collections`, so it cannot be reached through generic `/api/v1/*` CRUD. `AuthAdapter`
gains an optional `syncSchema?(): Promise<void>` lifecycle hook — `ForgeCmsRuntime.syncSchema()` now
calls it, which is what lets `ApiKeyAuthAdapter` provision its own table with no manual SQL.
`CompositeAuthAdapter` composes multiple `AuthAdapter`s (`new CompositeAuthAdapter([userAuth,
apiKeyAuth])`) so human sessions and machine keys authenticate through one configured adapter with zero
adapter-specific branching in `ForgeCmsRuntime`/`operations.ts`/`handlers.ts` — each strategy is tried
in order, and a token none of them recognize fails the same generic way a single adapter would.
`hasScope`/`hasAnyScope`/`hasAllScopes` read the new `scopes?: string[]` on `AuthUser`
(`@forge-cms/auth`) and the structurally-identical `CmsUser` (`@forge-cms/core`), so an existing
`access` function can write `hasScope(user, 'articles:read')` exactly like a role check — scopes are
opaque consumer strings; there is no scope registry and no automatic scope-to-CRUD mapping. No HTTP
management routes or admin/Angular UI were added (a consumer builds those on the programmatic
`createApiKey`/`listApiKeys`/`getApiKey`/`revokeApiKey`/`deleteApiKey` API if it needs them). One new
docs page, `apps/www/src/content/docs/machine-auth.md`. `scripts/verify-release.mjs`'s
`verifyRuntimeConsumer` now also proves `ApiKeyAuthAdapter`/`CompositeAuthAdapter`/`hasScope` work
through the packed public exports only. See
[docs/specs/048-machine-auth-api-keys.md](specs/048-machine-auth-api-keys.md).

**As of 2026-08-30, spec 049 hardens auth and runtime for real external consumers — a stabilization
branch, no new features.** Audited `@forge-cms/auth`, `@forge-cms/runtime`'s HTTP/access boundary,
`@forge-cms/db`/`@forge-cms/cloudflare` adapters, and `@forge-cms/core`'s access types against the
16-point acceptance brief in `docs/specs/049-auth-runtime-hardening.md`; classified every finding as a
bug, security hardening, contract inconsistency, test gap, doc gap, or no-change-needed rather than
rewriting anything speculatively. The one severe finding: `InMemoryDatabaseAdapter`,
`LibSqlDatabaseAdapter`, and `D1DatabaseAdapter` all cleared their internal collection registry on
every `syncSchema()` call; because `ApiKeyAuthAdapter` is meant to share the main `DatabaseAdapter`
instance (`apiKeyDatabase: database`, the documented and tested wiring), `ForgeCmsRuntime.syncSchema()`
calling `auth.syncSchema?.()` right after registering consumer collections silently wiped them out —
D1/libSQL then threw "not registered" on the next request, and InMemory silently stopped enforcing
unique constraints. `syncSchema()` now upserts by slug instead of clearing first, on all three
adapters. Two more real bugs: `CompositeAuthAdapter.requireAuth()` swallowed _any_ exception from a
child adapter (now only an expected `ForgeAuthError` falls through to the next strategy; an unexpected
one, e.g. a DB outage, propagates), and `@forge-cms/runtime`'s HTTP handlers
(`authorize`/`resolveOptionalUser`/`handlePreview`) had the identical bug one layer up — the fix that
matters most in practice, since a real consumer talks to HTTP, not the adapter directly. Security
hardening: `AuthAdapter` gained an optional `canHandleToken?(token)` so `CompositeAuthAdapter` can skip
a strategy that obviously doesn't own a token (no wasted DB round-trip/HMAC verify), implemented by
`ApiKeyAuthAdapter` and the signed-token-based adapters, fully backward compatible; `createApiKey` now
validates `name`/`expiresAt` and normalizes `scopes`; `revokeApiKey` is idempotent; `lastUsedAt` writes
are throttled (5 min default) instead of firing on every request; `_forge_*` is now a reserved
collection/global-slug prefix rejected by `defineCollection`/`defineGlobal`. Everything else audited —
secret handling, timing-safe comparison, scope-helper semantics, delete/update-of-missing-id
conventions, the `AuthUser`/`CmsUser` structural contract — was already correct and got regression
tests rather than churn. New coverage: `packages/runtime/src/machine-auth-integration.test.ts`
(machine principals reaching real collection/field/row-level access and the shared-adapter syncSchema
fix, through the actual runtime + HTTP pipeline, not just adapter-level unit tests), a 401-vs-403-vs-500
HTTP boundary suite in `handlers.test.ts`, and DB-adapter parity tests for `ApiKeyAuthAdapter` across
InMemory, libSQL, and D1 (`packages/auth/src/api-key.adapter.db-parity.test.ts`,
`packages/cloudflare/src/d1.adapter.test.ts`). No HTTP management routes, admin UI, or any other
feature expansion — see the spec's non-goals.

**Also as of 2026-08-30, spec 050 closes ROADMAP item 026 (query completeness)** — the next
stabilization branch after 049, no new feature area. `@forge-cms/db`'s `DatabaseWhere` gains nested
`{ and: [...] }` / `{ or: [...] }` groups (`packages/db/src/where.ts`) that compose with the existing
field operators (`eq`/`ne`/`gt`/`gte`/`lt`/`lte`/`in`/`contains`) and a new `containsValue` operator
for `relation({ many: true })` array-membership; `sort` accepts a field name (unchanged) or a
`{ field, order }[]` for a stable multi-field sort. `InMemoryDatabaseAdapter` (a new pure recursive
`matchesWhere`), `LibSqlDatabaseAdapter` (drizzle `and`/`or`, `containsValue` via `json_each`), and
`D1DatabaseAdapter` (parenthesized parameterized SQL, `containsValue` via
`EXISTS (SELECT 1 FROM json_each(...) WHERE value = ?)`) all implement identical semantics — proven by
a new shared cross-adapter contract suite, `runDatabaseAdapterQueryContractTests`
(`@forge-cms/testing/contracts`), run against InMemory, a real libSQL `:memory:` database, and a D1
mock extended in this branch with a real recursive-descent parenthesized-WHERE parser (previously it
only understood a flat `AND`-joined list). The Local API gains **`findOne()`**
(`find`/`findByID`/`findOne`/`count`/`create`/`update`/`delete`, typed and untyped) — the same
access/hooks/drafts/populate pipeline as `find`, `null` instead of throwing when nothing matches, a
real database-side `LIMIT 1` with no `count()` call. `find`/`count`/`findOne` share one new
`validateWhere`/`validateSort` gate (`packages/runtime/src/query-validation.ts`) that rejects unknown
fields/operators, `containsValue` on a non-relation field, and empty `and: []`/`or: []` groups as
stable `ForgeError`s (400) before anything reaches an adapter — closing a latent gap where an unknown
`where` field from trusted Local API code (not just HTTP) could 500 instead of 400, and where InMemory
silently matched nothing on a bad field while D1/libSQL threw. **Security-sensitive fix**: `mergeWhere`
(`access.ts`) no longer shallow-merges an access constraint with a caller's `where`
(`{ ...base, ...constraint }`, which could silently drop a key) — it now nests as
`{ and: [accessConstraint, requestedWhere] }`, so a caller-supplied `or` can never escape a row-level
access rule, with a new regression test proving it. **A second, more severe access-control bug was
caught by an independent review pass on this same branch, before merge**: an access-rule constraint
that legitimately resolves to `{ or: [] }` (e.g. `{ or: user.tenants.map(...) }` for a user belonging
to zero tenants — "no branch can ever be true", i.e. deny-all) bypasses `validateWhere` entirely (it
only validates the caller's own `where`), and the first-cut `LibSqlDatabaseAdapter`/`D1DatabaseAdapter`
compiled an empty `or` group to "no SQL condition at all" — returning every row in the table on the
only production adapter (D1) instead of none, while `InMemoryDatabaseAdapter` correctly returned zero
rows. Fixed by making every adapter (and `matchesWhere`) implement the standard empty-disjunction
identity (empty `or` → constant-false, not "no filter"), with a regression test run against both
InMemory and a real libSQL database. The same review also caught a where object mixing a flat key with
`and`/`or` at the same level silently dropping the flat key everywhere (`matchesWhere`, both SQL
builders, `validateWhere` all branched into "group xor flat" instead of evaluating every key — fixed by
iterating every key and AND-ing the results), an operator-name typo mixed with a valid operator
silently matching nothing instead of 400ing (`validateWhere` was checking `toOperatorValues`'s already-
sanitized output, which never surfaces an unknown operator — fixed by validating the raw condition
object's keys), and a leftover scratch investigation file that broke `format:check`/`test`. See
[docs/specs/050-query-completeness-and-adapter-parity.md](specs/050-query-completeness-and-adapter-parity.md)'s
Outcome section for the full list. HTTP transport: `?where=<url-encoded JSON>` (size-
capped at 4096 chars, strictly validated, replaces flat filter params for that request) and a
JSON-array `sort=` for multi-field sort — both additive, every existing flat query string is
unchanged. `@forge-cms/angular`'s `QueryOptions.where`/`sort` accept the same nested/multi-field
shapes through the existing shared `buildQueryString` helper (byte-identical URLs for existing flat
callers), and `CmsApiService.findOne()` calls the list endpoint with `limit: 1` — no new server route.
Typed Local API: `TypedWhere` recurses through `and`/`or` with field-name narrowing at every level,
`sort` accepts a typed multi-field list, `findOne` is fully typed. `and`/`or` are now reserved field
names, rejected by `validateCollectionIdentifiers` the same way system field names are. Verified via
the full gates, the extended contract suites, a real Playwright e2e pass (unaffected — no UI surface
changed), and `scripts/verify-release.mjs`'s packed-artifact consumer checks (extended with nested-
where/multi-sort/`findOne`/`containsValue` assertions that run against the real packed `.d.ts`/`.js`,
not source). One caveat was carried forward from this spec into 051 (below): `containsValue`'s
`json_each` SQL was, at the time, proven against a real SQLite engine for libSQL but only against a
hand-rolled D1 mock. See
[docs/specs/050-query-completeness-and-adapter-parity.md](specs/050-query-completeness-and-adapter-parity.md).

**One real bug found and fixed** (not just verified) — real D1's raw unique-constraint error message
carries a trailing diagnostic suffix (`table.col1, table.col2: SQLITE_CONSTRAINT (extended:
SQLITE_CONSTRAINT_UNIQUE)`) that the hand-rolled D1 mock's crafted error strings never included;
`@forge-cms/db`'s `parseSqliteUniqueConstraintMessage` naively split on `.`/`,` without stripping it,
corrupting the last column's name in a compound-unique conflict — a real bug that would have leaked
that diagnostic text into `UniqueConstraintError.fields` and hence into the public HTTP error
response's `details`. Fixed (`packages/db/src/constraint-error.ts`), covered by a new
`packages/db/src/constraint-error.test.ts`, and fed back into the D1 test mock
(`d1.adapter.test.ts`'s `MockD1Database`) so this bug class is now caught by the fast unit suite too,
not only the slower real-D1 integration suite.

**Also fixed, a pre-existing architecture violation found during the audit, not a Cloudflare-specific
bug**: deleting an upload-enabled document's underlying storage object used to happen only in
`handlers.ts` (the HTTP layer) — a direct Local API caller (server code, a hook, a seed script)
orphaned the object. Moved into `operations.ts`'s `deleteDocument` itself (storage deleted only after
the database delete succeeds, never on a denied/failed delete, best-effort/log-only on cleanup
failure), matching CLAUDE.md's "business logic lives in the Local API" rule; `handlers.ts`'s
`handleDelete` dropped its now-duplicate copy. Covered by InMemory tests
(`packages/runtime/src/operations.test.ts`) and a real-R2 integration test

## API surface (implemented in apps/www server routes)

- `GET /api/v1/[collection]` — list (supports `limit`, `offset`, `where` filters via any other query
  param — bare `field=value` for equality or `field[op]=value` for
  `ne`/`gt`/`gte`/`lt`/`lte`/`in`(comma-separated)/`contains`, coerced to the field's type, **spec 011,
  2026-07-20** — plus single-field `sort`/`order` (`asc`/`desc`), `depth=1` to populate `relation`
  fields with the actual related record instead of a bare id (**spec 012**), and — on collections with
  `drafts: true` — `status=draft|published|all` to control which documents are visible, gated on
  authentication (**spec 017, 2026-07-20**)); `POST /api/v1/[collection]` — create (validated, **requires
  admin or editor role**; accepts `multipart/form-data` on `upload: true` collections, **spec 016**)
- `GET /api/v1/[collection]/[id]` — read (also supports `depth=1`; 404s a `draft` document for
  unauthenticated requests on a `drafts: true` collection, spec 017); `PUT`/`DELETE
/api/v1/[collection]/[id]` — update/delete (validated, **require admin or editor role**)
- `GET /api/v1/collections` — collection metadata (+ `fieldDefinitions`, added 2026-07-07)
- `GET /api/auth/me` — current user; `POST /api/auth/login` — `{ email, password }` →
  `{ token, user }` (added 2026-07-08, spec 006)
- `GET /api/auth/users` — list users; `POST /api/auth/users` — create user;
  `PUT /api/auth/users/:id` — update user; `DELETE /api/auth/users/:id` — delete user
  (added 2026-07-20, spec 009; **admin-only as of spec 010**)
- `GET /api/status` — adapter/API health info

✅ **Routes now delegate to `@forge-cms/runtime`'s handlers** (spec 007, 2026-07-08) — matches
ARCHITECTURE.md's "thin wrappers" claim; known issue #1 resolved. Success envelope: list
`{ data, meta }`, item `{ data }` (create → `201`), delete `204`. Error envelope matches
ARCHITECTURE.md: `{ error: string, details?: ValidationError[] }`.

## Infrastructure

- CI/CD (GitHub Actions): **consolidated into a single pipeline `ci.yml` as of 2026-07-24.** One
  `checks` job (format:check + lint + typecheck + test + build + Playwright e2e) runs on every push/PR
  to main; a `deploy` job `needs: checks` and is gated `if: github.event_name == 'push' && github.ref ==
'refs/heads/main'`, so PRs and forks never deploy. It builds `apps/www`, verifies
  `apps/www/dist/analog/public/index.html`, then `wrangler pages deploy`s to Cloudflare Pages
  (`--project-name=forge-cms`); needs `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` secrets and uses
  a `production` environment (url `https://forge-cms.pages.dev`). The old separate `e2e.yml` and
  `deploy-cloudflare.yml` were removed — before, every push to main triggered three overlapping
  workflow runs; now it's exactly one. **Cloudflare is the only deploy target.** **As of 2026-07-27 a
  second deploy job, `deploy-demo`, publishes `apps/demo-aesthetics` to its own Pages project
  `forge-cms-demo`** (`https://forge-cms-demo.pages.dev`, environment `production-demo`) under the
  same guard and the same two secrets; it creates the project on first run and deploys via
  `wrangler pages deploy --cwd apps/demo-aesthetics` (there is no `--config` flag for `pages deploy`,
  so `--cwd` is how a monorepo selects a second project's `wrangler.toml`). That config binds D1
  (`forge-cms-demo`) and R2 (`forge-cms-demo-media`) as **`DB`** and **`BUCKET`** — the names
  `getServerRuntime` checks before falling back to the in-memory adapters, so renaming either one
  degrades the deploy silently. (Earlier, the
  duplicate ungated `deploy.yml` had already been removed per spec 002.)
- Changesets configured; public packages are aligned to `0.0.1` for the first release baseline, with
  packed-artifact verification in `pnpm release:verify`.
- `wrangler.toml`: Pages config, output `apps/www/dist/analog/public` (Nitro `cloudflare-pages`
  preset — includes `_worker.js`, the compiled API server), `nodejs_compat`.

## Known issues / debt (verified 2026-07-22)

1. ~~`handleUpdate` partial-validation bug~~ — **fixed 2026-07-19.** Required fields already present on
   the stored record are no longer required in a partial PUT body.
2. ~~`@forge-cms/admin` is dead code~~ — **fixed 2026-07-08, spec 008.** The real layout/document-list/
   schema-driven-form components now live in the package; `apps/www` consumes them.
3. `_routes.json`/`_headers`/`_redirects` (Nitro's Cloudflare Pages preset output) land in
   `apps/www/dist/analog/` instead of inside `apps/www/dist/analog/public/`, so they're not included
   in the deploy — cosmetic only (the worker itself already serves static assets via `env.ASSETS`
   regardless), noted as a non-goal follow-up in spec 002.
4. `@forge-cms/cloudflare` previously depended on `@forge-cms/runtime` — **fixed 2026-07-19.**
5. `README.md` and root `CHANGELOG.md` were outdated — **fixed 2026-07-19.**
6. D1 `findMany` did not coerce `where` values before binding — **fixed 2026-07-19.**
7. `/api/auth/me` rebuilt the request manually — **fixed 2026-07-19**, now uses `toWebRequest`.
8. `toWebRequest(event)` consumed the request body before `readBody(event)` in `POST`/`PUT` auth routes,
   causing those routes to hang — **fixed 2026-07-20** by building a headers-only `Request` for auth
   validation after the body is read.
9. ~~Role-based access control~~ — **fixed 2026-07-20, spec 010.** Roles are now enforced in the
   backend (`/api/auth/users` admin-only, `/api/v1/*` writes restricted to admin/editor) and the
   admin UI hides write actions and the Users page for unauthorized roles.
10. ~~Production-only crash on every `/admin` page: `Error: JIT compiler unavailable`~~ — **fixed
    2026-07-20.** Two independent causes, both fixed inside this repo without touching any external
    package: - `@forge-cms/admin` and third-party libraries like `@voltui/components` build with
    `angularCompilerOptions.compilationMode: "partial"` (the correct choice for a publishable
    library — it isn't pinned to one exact Angular compiler version). Partial compilation ships
    `ɵɵngDeclareComponent`-style calls that require the consuming app's build to run the **Angular
    linker**. `apps/www`'s Vite/Analog.js pipeline had no linker step, so those declarations reached
    production unlinked; AOT prod builds tree-shake `@angular/compiler` out entirely, so Angular's
    runtime JIT fallback threw. Fixed by adding a real Angular linker to `apps/www`'s Vite build:
    `apps/www/vite-plugins/angular-linker.ts` runs `@angular/compiler-cli/linker/babel` (the
    officially documented way to integrate the linker outside the Angular CLI) over any dependency
    file that `@angular/compiler-cli/linker`'s `needsLinking` flags — this fixes every partial-Ivy
    dependency in the graph, present and future, without changing any library's compilation mode. - Separately, `@forge-cms/angular` built with plain `tsc`, not `ngc`, so `CmsApiService`'s
    `@Injectable({ providedIn: 'root' })` was never processed by Angular's compiler at all — it
    shipped as a raw runtime decorator with no static `ɵprov`, which also needs JIT (a different
    failure mode from the linking issue above, same underlying "AOT prod builds have no
    `@angular/compiler`" cause). Fixed by switching its build to `ngc` with
    `compilationMode: "partial"` (consistent with `@forge-cms/admin`); the same linker plugin
    resolves it at `apps/www`'s build time. - Verified with a real browser (Playwright) against the actual `wrangler pages dev`-served
    production build: landing, login (rendering real `@voltui/components`), and `/admin/dashboard`
    all load with zero console errors. - ~~Found but not fixed: local D1 login returns `500 D1_ERROR: table users has no column named
passwordHash`~~ — **fixed 2026-07-22, spec 018.** `@forge-cms/auth` now exports
    `withAuthFields()`, which merges the columns the auth adapter writes into the `users`
    collection definition, so schema generation and additive migration cover them. A regression
    test asserts the generated SQL contains `"passwordHash" TEXT`.

11. **`meta.count` is the page length, not the total** — **fixed 2026-07-22, spec 018.**
    `DatabaseAdapter.count` takes a `where`, and list responses carry `totalDocs`/`page`/
    `totalPages`/`hasNextPage`/`hasPrevPage`.
12. **The admin relation field is a bare text input** where you paste a document id by hand, and
    `richtext`/`upload` fall back to a textarea/text input. Composite fields render properly
    (spec 022) but scalar widgets are still primitive — ROADMAP item 032.
13. **No versions/revisions.** Spec 017 shipped draft/published status only: no history, no diff, no
    restore, no autosave — ROADMAP item 024.
14. **No globals** (singleton documents). `apps/www` fakes one with a `site_config` collection —
    ROADMAP item 023.
15. **No localisation.** Changes the storage shape, so it gets more expensive the longer real data
    exists — ROADMAP item 025.
16. **Deleting a document does not delete its storage object**, and relations are not
    referentially checked on delete (a deleted author leaves posts pointing at a dead id). Spec 021's
    `beforeDelete`/`afterDelete` hooks now make both expressible in userland, but neither is built in
    — ROADMAP item 027.
17. ~~`DatabaseAdapter.syncSchema()` cleared its internal collection registry on every call~~ — **found
    and fixed 2026-08-30, spec 049.** Harmless as long as `syncSchema()` was only ever called once with
    the full collection set — which is what every existing app/test did — but a second call with a
    _different_ set (exactly what `ApiKeyAuthAdapter.syncSchema()` does when it shares the main
    `DatabaseAdapter` instance, the documented wiring) silently unregistered every consumer collection:
    D1/libSQL then threw "not registered" on the next request, InMemory silently stopped enforcing
    unique constraints. All three adapters (`InMemoryDatabaseAdapter`, `LibSqlDatabaseAdapter`,
    `D1DatabaseAdapter`) now upsert by slug instead of clearing first.

## What's next

Work is planned in [ROADMAP.md](ROADMAP.md), which sequences the remaining gaps by cost-of-delay.
Each numbered item there gets its own spec in `docs/specs/` when picked up, per [SDD.md](SDD.md).

**Read [DEMO-FINDINGS.md](DEMO-FINDINGS.md) alongside it.** It is the only document here written from
building a real site rather than from reasoning about one. Its client-side half (roadmap 036) is now
partly delivered by spec 041 — signals resources and a full query API, but **not** SSR-safe fetch or
transfer state, which remain the largest single gap for a content site.

Status as of 2026-08-30:

- **Phase 0 — Unblock:** 0.1 (D1 auth schema) and 0.2 (pagination metadata) done via spec 018.
  **0.3 (prepare/publish `0.0.1` to npm) is in progress via spec 045**. Publication still needs
  registry credentials and `@forge-cms` scope access. **Specs 046 (compound indexes/schema integrity,
  2026-08-26), 047 (typed Local API, 2026-08-27), 048 (machine auth / API keys, 2026-08-28), 049 (auth/
  runtime hardening, 2026-08-30), and 050 (query completeness & adapter parity, 2026-08-30) all
  prepare the next release** — each has its own changeset in place (046's a `patch`, 047's a `minor`,
  048's `minor` for `@forge-cms/auth`/`@forge-cms/core` and `patch` for `@forge-cms/runtime`, 049's a
  `patch` across `@forge-cms/core`/`db`/`auth`/`runtime`/`cloudflare`, 050's a `minor` across
  `@forge-cms/core`/`db`/`cloudflare`/`runtime`/`angular`/`testing` — all across the fixed public
  package family, so the family bumps together at the highest of them); the actual version bump and
  npm publish happen via the existing automated Changesets Release PR in CI on merge to `main`, same
  as every other package change, not as a manual step in any of them.
- **Phase 1 — Structural core: done.** Specs 019 (Local API), 020 (access as functions),
  021 (full hook pipeline), 022 (composite fields).
- **Phase 2 — Content model:** globals (0.3.1), versions/revisions (0.3.2, status only — no diff/
  restore/autosave), localisation (0.3.4), and referential integrity (0.3.5) shipped earlier as
  Phase-0.3.x hardening; **query completeness (nested `and`/`or`, multi-field sort, `findOne`,
  relation-array membership) is done via spec 050, 2026-08-30** — the last item in this phase's
  original scope.
- **Phase 3 — Auth & DX:** real auth (cookies/refresh/password reset/API keys), an email adapter,
  a config + plugin system, a CLI. Not started.
- **Phase 4 — Admin UI:** real field widgets (richtext editor, media picker, searchable relation
  picker), list-view pagination/sort/filters, conditional fields, live preview. Not started.
- **Phase 5 — The Angular/Analog moat:** signals-based client resources, an Analog integration
  package, collection types reaching the client without codegen. Not started — but per ROADMAP's
  thesis these rank in strategic value immediately after Phase 1, ahead of most of Phases 2–4,
  because they are the reason to choose ForgeCMS over an existing CMS at all.
